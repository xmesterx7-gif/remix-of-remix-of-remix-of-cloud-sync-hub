# دوچرخه یار

تو یک مهندس ارشد محصول، طراح UI/UX و برنامه‌نویس Full-Stack هستی. مأموریت تو این است که یک اپلیکیشن وب کامل، حرفه‌ای، بدون نقص، قابل نصب روی موبایل، آیفون و ویندوز، با طراحی موبایل‌فرست و کاملاً ریسپانسیو بسازی.

نام محصول:
«سامانه مدیریت فروشگاه و تعمیرگاه دوچرخه»

هدف محصول:
ما یک فروشگاه و تعمیرگاه دوچرخه داریم. این سامانه باید برای استفاده روزمره مدیر اصلی، مدیر فروشگاه، فروشنده‌ها، کارمندها، شرکا و تعمیرکارها باشد. کاربران باید بتوانند حین کار مواردی مثل خرید دوچرخه، هزینه‌ها، وظایف کارگران و فاکتورهای خرید را ثبت کنند. اطلاعات ثبت‌شده باید با نوتیفیکیشن/الارم به افراد مرتبط ارسال شود و در نهایت خروجی‌های مناسب برای انتقال به برنامه حسابداری اصلی تولید شود.

========================
1) الزامات کلی محصول
========================

- اپلیکیشن باید Web App / PWA باشد.
- کاملاً Mobile-First باشد.
- روی موبایل اندروید، آیفون، تبلت و ویندوز/دسکتاپ کاملاً ریسپانسیو و بدون به‌هم‌ریختگی باشد.
- رابط کاربری 100% فارسی و RTL باشد.
- فونت فارسی استاندارد مثل Vazirmatn استفاده شود.
- تاریخ‌ها شمسی/جلالی باشند.
- فرمت پول تومان باشد، ولی در تنظیمات امکان تغییر به ریال هم وجود داشته باشد.
- اپلیکیشن باید نصب‌شونده باشد: manifest.json، Service Worker، آیکون‌ها، splash screen و حالت standalone داشته باشد.
- در آیفون باید safe-area، notch، دکمه‌های بزرگ لمسی و طراحی مناسب iOS رعایت شود.
- در ویندوز/دسکتاپ باید Sidebar یا Navigation مناسب، جدول‌ها، فیلترها و فرم‌های بزرگ‌تر نمایش داده شوند.
- اپ باید سریع، سبک، ساده و برای کاربران غیرفنی قابل فهم باشد.
- تمام حالت‌های UI شامل Loading، Empty، Error، Success، Confirm Dialog، Toast و Skeleton باید طراحی شوند.
- هیچ صفحه‌ای نباید بدون حالت خطا، لودینگ یا Empty باشد.
- طراحی باید تمیز، مدرن، ساده و فروشگاهی باشد.
- رنگ‌بندی باید خوانا و مناسب کسب‌وکار باشد.
- دسترسی‌پذیری تا حد ممکن رعایت شود: کنتراست مناسب، لیبل فرم‌ها، دکمه‌های بزرگ، فوکوس کیبورد و پیام‌های خطای واضح.
- اگر بخشی از نیازمندی مبهم بود، بهترین راه‌حل استاندارد را انتخاب کن و آن را در README مستند کن.
- هیچ بخشی را با TODO، placeholder، کد ناقص یا «بعداً اضافه می‌شود» رها نکن.
- تمام کدها باید قابل اجرا باشند و پروژه باید با دستورات ساده نصب و اجرا شود.

========================
2) استک فنی پیشنهادی و اجباری
========================

از این استک استفاده کن:

- Next.js نسخه جدید با App Router
- TypeScript
- React
- Tailwind CSS
- Prisma ORM
- دیتابیس: SQLite برای توسعه ساده، اما ساختار طوری باشد که با PostgreSQL هم به‌راحتی کار کند.
- احراز هویت: NextAuth با Credentials Provider
- اعتبارسنجی فرم‌ها و APIها: Zod
- رمز عبور: bcrypt یا bcryptjs
- تاریخ شمسی: date-fns-jalali یا کتابخانه مشابه و سبک
- نوتیفیکیشن داخل برنامه: Notification Center + Badge + Toast
- نوتیفیکیشن Push واقعی: Web Push + Service Worker + VAPID
- خروجی Excel/CSV: کتابخانه مناسب مثل xlsx یا exceljs
- خروجی JSON و CSV UTF-8 با BOM برای سازگاری با Excel فارسی
- فرم‌ها: React Hook Form + Zod Resolver
- state/server state: React Query یا SWR
- استایل‌ها: Tailwind CSS و کامپوننت‌های تمیز
- برای پرینت/PDF: استفاده از Print CSS و دکمه پرینت؛ نیازی به کتابخانه سنگین PDF نیست، مگر ضروری باشد.

اگر برای اجرای کامل بعضی قابلیت‌ها نیاز به محیط变量 یا کلید بود، فایل .env.example کامل بساز و در README توضیح بده.

========================
3) نقش‌ها و دسترسی‌ها
========================

نقش‌های سیستم:

1. ADMIN
   - مدیر اصلی و مالک.
   - به همه بخش‌ها دسترسی کامل دارد.
   - می‌تواند کاربران را مدیریت کند.
   - می‌تواند رکوردها را تأیید نهایی، رد یا به‌عنوان «ثبت‌شده در حسابداری» علامت‌گذاری کند.
   - می‌تواند خروجی‌های حسابداری بگیرد.
   - می‌تواند تنظیمات سیستم را تغییر دهد.

2. STORE_MANAGER
   - مدیر فروشگاه، مثلاً «علی».
   - به بیشتر بخش‌ها دسترسی دارد، اما نه همه.
   - می‌تواند وظایف کارگران را ایجاد کند.
   - می‌تواند دستمزد وظایف را مشخص کند.
   - می‌تواند وضعیت وظایف انجام‌شده را بررسی، تأیید، رد یا اصلاح کند.
   - می‌تواند فاکتور خرید/پیش‌فاکتور خرید ایجاد کند.
   - می‌تواند بعد از خرید، قیمت نهایی و تعداد نهایی فاکتور خرید را ثبت کند.
   - می‌تواند خرید دوچرخه و هزینه‌های مرتبط را مشاهده کند.
   - نمی‌تواند کاربران را حذف کند یا دسترسی‌های حساس سیستمی را تغییر دهد.
   - نمی‌تواند چیزی را به‌عنوان «ثبت نهایی در حسابداری اصلی» علامت‌گذاری کند؛ این کار فقط با ADMIN است.

3. EMPLOYEE
   - فروشنده یا کارمند عمومی.
   - می‌تواند خرید دوچرخه ثبت کند.
   - می‌تواند هزینه‌های کاری را ثبت کند.
   - می‌تواند ثبت‌های خودش را ببیند.
   - به بخش‌های مدیریتی، کاربران، تنظیمات و خروجی حسابداری دسترسی ندارد.
   - اگر برای او وظیفه‌ای ثبت شد، فقط وظایف خودش را ببیند.

4. MECHANIC
   - تعمیرکار.
   - وقتی وارد برنامه می‌شود فقط بخش وظایف خودش را ببیند.
   - فقط وظایفی که به او محول شده را مشاهده کند.
   - بتواند وضعیت وظیفه را تغییر دهد و انجام کار را ثبت کند.
   - به خرید دوچرخه، فاکتور خرید، هزینه‌ها، داشبورد مدیریتی و سایر بخش‌ها دسترسی نداشته باشد.
   - فقط نوتیفیکیشن‌های مرتبط با وظایف خودش را ببیند.

قوانین دسترسی:
- دسترسی‌ها باید سمت سرور کنترل شوند، نه فقط در UI.
- منوها و صفحات باید بر اساس نقش کاربر نمایش داده شوند.
- اگر کاربری به صفحه‌ای دسترسی نداشت، باید به صفحه مناسب نقش خودش هدایت شود.
- تمام actionها باید permission check سمت سرور داشته باشند.
- نقش‌ها باید قابل گسترش باشند، ولی برای نسخه اول همین چهار نقش کافی است.

========================
4) صفحات مورد نیاز
========================

حداقل صفحات زیر ساخته شوند:

1. /login
   - ورود با نام کاربری/شماره موبایل و رمز عبور.
   - طراحی ساده، فارسی، مناسب موبایل.
   - پیام خطای واضح برای اطلاعات اشتباه.
   - امکان نمایش/مخفی کردن رمز عبور.

2. /dashboard
   - داشبورد بر اساس نقش کاربر.
   - برای ADMIN و STORE_MANAGER: کارت‌های خلاصه، کارهای در انتظار تأیید، خریدهای اخیر، هزینه‌های اخیر، وظایف در حال انجام، فاکتورهای نیازمند بررسی.
   - برای EMPLOYEE: خلاصه ثبت‌های خود، خریدهای اخیر خود، هزینه‌های اخیر خود، وظایف احتمالی خودش.
   - برای MECHANIC: فقط لیست وظایف خودش و وضعیت آن‌ها.

3. /bicycle-purchases
   - لیست خریدهای دوچرخه.
   - فیلتر بر اساس وضعیت، تاریخ، برند، نوع، ثبت‌کننده.
   - جستجو.
   - برای ADMIN/STORE_MANAGER: مشاهده همه.
   - برای EMPLOYEE: فقط مشاهده ثبت‌های خودش، مگر دسترسی بیشتری داده شود.

4. /bicycle-purchases/new
   - فرم ثبت خرید دوچرخه.

5. /bicycle-purchases/[id]
   - جزئیات خرید دوچرخه.
   - نمایش وضعیت، ثبت‌کننده، تاریخ، تأییدکننده، توضیحات، تاریخچه تغییرات.
   - دکمه تأیید، رد، ویرایش، علامت‌گذاری به‌عنوان ثبت‌شده در حسابداری برای ADMIN.

6. /expenses
   - لیست هزینه‌ها.
   - فیلتر بر اساس دسته، وضعیت، تاریخ، کاربر.
   - جستجو.

7. /expenses/new یا modal/bottom sheet
   - فرم ثبت هزینه.

8. /tasks
   - برای ADMIN/STORE_MANAGER: لیست کارگران و کاربران وظیفه‌گیرنده.
   - برای MECHANIC/EMPLOYEE: فقط لیست وظایف خودشان.

9. /tasks/workers یا /tasks/[workerId]
   - برای مدیر/مدیر فروشگاه:
     - انتخاب کارگر از لیست.
     - مشاهده وظایف در حال انجام، انجام‌نشده، ارسال‌شده، تأییدشده، رده شده.
     - ایجاد وظیفه جدید برای آن کارگر.

10. /tasks/[id]
   - جزئیات وظیفه.
   - تغییر وضعیت.
   - ثبت انجام کار توسط تعمیرکار.
   - تأیید، رد یا اصلاح توسط مدیر/مدیر فروشگاه.
   - ثبت دستمزد، توضیحات، تاریخ سررسید، اولویت.

11. /purchase-invoices
   - لیست فاکتورهای خرید/پیش‌فاکتورها.
   - وضعیت‌ها: پیش‌فاکتور، خرید انجام شده، در انتظار نهایی‌سازی، نهایی شده، ثبت شده در حسابداری.

12. /purchase-invoices/new
   - ایجاد پیش‌فاکتور خرید.

13. /purchase-invoices/[id]
   - مشاهده و تکمیل فاکتور خرید.
   - ثبت قیمت نهایی و تعداد نهایی برای هر آیتم.
   - نمایش تفاوت قیمت احتمالی و قیمت نهایی.
   - دکمه نهایی‌سازی.
   - بعد از نهایی‌سازی، ارسال نوتیفیکیشن فوری به ADMIN.

14. /notifications
   - مرکز نوتیفیکیشن‌ها.
   - نمایش خوانده‌شده/خوانده‌نشده.
   - لینک به صفحه مرتبط.
   - دکمه علامت‌گذاری همه به‌عنوان خوانده‌شده.

15. /users
   - فقط ADMIN.
   - لیست کاربران.
   - ایجاد کاربر جدید.
   - ویرایش نام، نام کاربری، شماره موبایل، نقش، وضعیت فعال/غیرفعال.
   - ریست رمز عبور.
   - غیرفعال کردن کاربر.

16. /settings
   - فقط ADMIN.
   - تنظیمات واحد پول.
   - تنظیمات نوتیفیکیشن‌ها.
   - تنظیمات خروجی حسابداری.
   - تنظیمات نگاشت فیلدها برای خروجی حسابداری.
   - تنظیمات Telegram/SMS/Webhook در صورت وجود.

17. /exports
   - مرکز خروجی حسابداری.
   - فقط ADMIN، و در صورت صلاحیت STORE_MANAGER فقط برای مشاهده/خروجی بخش‌های مرتبط.
   - انتخاب بازه تاریخ شمسی.
   - انتخاب نوع خروجی:
     - خرید دوچرخه تأییدشده
     - هزینه‌های تأییدشده
     - دستمزد وظایف تأییدشده
     - فاکتورهای خرید نهایی‌شده
     - خروجی ترکیبی همه موارد
   - فرمت خروجی:
     - CSV UTF-8
     - Excel XLSX
     - JSON
   - دکمه پرینت/PDF.
   - امکان علامت‌گذاری رکوردها به‌عنوان «منتقل‌شده به حسابداری».
   - امکان وارد کردن شماره سند حسابداری برای هر رکورد.

========================
5) ماژول خرید دوچرخه
========================

فرم ثبت خرید دوچرخه باید این فیلدها را داشته باشد:

- سایز دوچرخه: اجباری
- برند: اجباری
- رنگ: اجباری
- نوع دوچرخه: select با گزینه‌های:
  - دخترانه
  - پسرانه
  - اسپرت
  - مقدار پیش‌فرض: اسپرت
- قیمت خرید: اجباری، عددی، واحد تومان
- توضیحات: اختیاری
- تاریخ ثبت: خودکار شمسی
- ثبت‌کننده: خودکار
- وضعیت: به‌صورت پیش‌فرض PENDING

قابلیت‌ها:
- لیست خریدها با جستجو و فیلتر.
- مشاهده جزئیات.
- ویرایش توسط کاربر مجاز تا قبل از تأیید نهایی.
- تأیید توسط ADMIN یا STORE_MANAGER.
- رد کردن با دلیل اجباری.
- بعد از تأیید، نوتیفیکیشن به ثبت‌کننده ارسال شود.
- بعد از ایجاد خرید دوچرخه، نوتیفیکیشن/الارم برای ADMIN و STORE_MANAGER ارسال شود.
- ADMIN بتواند وضعیت را به SYNCED_TO_ACCOUNTING تغییر دهد و شماره سند حسابداری را ثبت کند.
- خروجی حسابداری از خریدهای تأییدشده گرفته شود.

========================
6) ماژول ثبت هزینه و دکمه + بزرگ
========================

یک دکمه + بزرگ، شناور و مناسب دسترسی انگشت شست در پایین صفحه موبایل طراحی کن.

وقتی کاربر روی دکمه + می‌زند، یک Bottom Sheet یا Action Sheet باز شود.

در این منو باید به ترتیب این گزینه‌ها نمایش داده شوند:

1. ثبت هزینه
   - وقتی روی «ثبت هزینه» می‌زند، زیرمجموعه‌های زیر نمایش داده شوند:
     - حقوق
     - پاداش
     - جریمه
     - برداشت شخصی
     - هزینه متفرقه

2. اگر کاربر نقش مجاز داشت، گزینه‌های زیر هم نمایش داده شوند:
   - ثبت خرید دوچرخه
   - ثبت پیش‌فاکتور خرید
   - ثبت وظیفه جدید

قوانین نمایش دکمه +:
- برای ADMIN و STORE_MANAGER همه گزینه‌های مجاز نمایش داده شوند.
- برای EMPLOYEE حداقل «ثبت هزینه» و «ثبت خرید دوچرخه» نمایش داده شود.
- برای MECHANIC دکمه + یا مخفی باشد یا فقط گزینه «ثبت انجام وظیفه» را نشان دهد، چون تعمیرکار فقط باید بخش وظایف خودش را ببیند.
- اگر نقشی به ثبت هزینه دسترسی ندارد، گزینه ثبت هزینه برای آن نقش نمایش داده نشود.

فرم ثبت هزینه باید این فیلدها را داشته باشد:

- دسته هزینه: اجباری
  - حقوق
  - پاداش
  - جریمه
  - برداشت شخصی
  - هزینه متفرقه
- مبلغ: اجباری، عددی، تومان
- تاریخ: شمسی، پیش‌فرض امروز، قابل تغییر
- توضیحات: اختیاری
- کاربر مرتبط: اختیاری، برای مواردی مثل حقوق، پاداش، جریمه
- ثبت‌کننده: خودکار
- وضعیت: PENDING
- تصویر رسید یا عکس: اختیاری
- اگر تصویر آپلود شد، ذخیره امن فایل و نمایش کوچک در جزئیات.

قوانین ثبت هزینه:
- ثبت هزینه توسط کاربران مجاز انجام شود.
- «برداشت شخصی» فقط برای ADMIN و STORE_MANAGER قابل ثبت باشد.
- سایر دسته‌ها بسته به نقش قابل تنظیم باشند.
- بعد از ثبت هزینه، نوتیفیکیشن برای ADMIN ارسال شود.
- اگر دسته هزینه حقوق/پاداش/جریمه بود، نوتیفیکیشن برای STORE_MANAGER هم ارسال شود.
- ADMIN یا STORE_MANAGER بتوانند هزینه را تأیید یا رد کنند.
- هزینه رد شده باید دلیل رد داشته باشد.
- هزینه تأیید شده قابل خروجی حسابداری باشد.
- فقط ADMIN بتواند هزینه را به‌عنوان ثبت‌شده در حسابداری اصلی علامت‌گذاری کند.

========================
7) ماژول وظایف کارگر / تعمیرکار
========================

این بخش باید بسیار مهم و دقیق پیاده‌سازی شود.

هدف:
مدیر فروشگاه یا مدیر اصلی بتواند برای کارگران/تعمیرکارها وظیفه تعریف کند، دستمزد تعیین کند، وضعیت را پیگیری کند و بعد از انجام کار، تأیید یا اصلاح کند.

ساختار نمایش برای مدیر/مدیر فروشگاه:
- صفحه‌ای شامل لیست کارگران/کاربران دارای نقش MECHANIC یا کاربرانی که به‌عنوان worker علامت‌گذاری شده‌اند.
- روی هر اسم کارگر که کلیک شد، صفحه پروفایل کاری او باز شود.
- در صفحه هر کارگر:
  - وظایف انجام‌نشده
  - وظایف در حال انجام
  - وظایف ارسال‌شده و منتظر تأیید
  - وظایف تأییدشده
  - وظایف رد شده
  - دکمه ایجاد وظیفه جدید برای همان کارگر

فرم ایجاد وظیفه جدید:
- انتخاب کارگر: اجباری
- عنوان وظیفه: اجباری
- توضیحات وظیفه: اختیاری
- اولویت: کم / متوسط / زیاد / فوری
- تاریخ سررسید: شمسی، اختیاری یا اجباری بسته به طراحی، ولی پیشنهاداً اختیاری
- دستمزد: عددی، تومان، می‌تواند اجباری یا اختیاری باشد؛ برای حالت فروشگاه دوچرخه بهتر است اجباری یا حداقل بسیار مهم باشد.
- وضعیت اولیه: PENDING
- ایجادکننده: خودکار

وضعیت‌های وظیفه:
- PENDING: هنوز شروع نشده
- IN_PROGRESS: در حال انجام
- SUBMITTED: تعمیرکار انجام داد و منتظر تأیید مدیر است
- APPROVED: مدیر تأیید کرده
- REJECTED: مدیر رد کرده و نیاز به اصلاح دارد
- CANCELLED: لغو شده
- SYNCED_TO_ACCOUNTING: به حسابداری اصلی منتقل شده

دید تعمیرکار/کارگر:
- وقتی MECHANIC وارد برنامه می‌شود، فقط بخش وظایف خودش را ببیند.
- لیست وظایف او باید شامل:
  - وظایف انجام‌نشده
  - وظایف در حال انجام
  - وظایف انجام‌شده/ارسال‌شده
  - وظایف تأییدشده
  - وظایف رد شده
- تعمیرکار نباید به داشبورد مدیریتی، هزینه‌ها، فاکتورها، خرید دوچرخه، کاربران و تنظیمات دسترسی داشته باشد.
- تعمیرکار بتواند:
  - وظیفه را شروع کند: تغییر به IN_PROGRESS
  - انجام وظیفه را ثبت کند: تغییر به SUBMITTED
  - توضیحات انجام کار را وارد کند.
  - در صورت نیاز هزینه قطعات یا نکته را ثبت کند، اما این بخش نباید پیچیده شود؛ فعلاً توضیحات کافی است.
- بعد از ثبت انجام وظیفه توسط تعمیرکار، نوتیفیکیشن فوری برای ADMIN و STORE_MANAGER ارسال شود.

دید مدیر برای تأیید:
- مدیر/مدیر فروشگاه بتواند وظیفه SUBMITTED را ببیند.
- بتواند:
  - تأیید کند.
  - رد کند.
  - اصلاحیه وارد کند.
  - دستمزد نهایی را تغییر دهد.
  - توضیحات تأیید را ثبت کند.
- اگر رد شد، دلیل رد اجباری باشد و نوتیفیکیشن به تعمیرکار برود.
- اگر تأیید شد، نوتیفیکیشن به تعمیرکار برود و وضعیت APPROVED شود.
- فقط ADMIN بتواند وضعیت SYNCED_TO_ACCOUNTING را ثبت کند.

========================
8) ماژول فاکتور خرید / پیش‌فاکتور خرید
========================

این بخش برای مدیر فروشگاه و مدیر اصلی است.

نیاز اصلی:
یک پیش‌فاکتور خرید در برنامه ثبت می‌شود. سپس خرید واقعی انجام می‌شود. بعد مدیر فروشگاه باید قیمت نهایی و تعداد نهایی را ثبت کند. سپس نوتیفیکیشن فوری به مدیر اصلی ارسال شود تا آن را به برنامه حسابداری اصلی منتقل کند.

فرم ایجاد پیش‌فاکتور خرید:

فیلدهای سربرگ:
- شماره پیش‌فاکتور: خودکار یا دستی، یکتا
- تأمین‌کننده/فروشنده: اختیاری
- تاریخ: شمسی، پیش‌فرض امروز
- توضیحات: اختیاری
- ایجادکننده: خودکار
- وضعیت: PRE_INVOICE یا DRAFT

آیتم‌های پیش‌فاکتور:
هر آیتم باید این فیلدها را داشته باشد:
- نام محصول: اجباری
- تعداد خرید احتمالی: اجباری، عددی
- قیمت واحد احتمالی: اجباری، عددی، تومان
- توضیحات آیتم: اختیاری

امکان افزودن چند آیتم به یک فاکتور وجود داشته باشد.
جمع کل احتمالی باید محاسبه و نمایش داده شود.

بعد از خرید واقعی:
- STORE_MANAGER یا ADMIN وارد فاکتور شود.
- برای هر آیتم یکی‌یکی این موارد را ثبت کند:
  - تعداد نهایی
  - قیمت واحد نهایی
- اگر قیمت یا تعداد تغییر نکرده باشد، بتواند با یک دکمه «کپی از مقادیر اولیه» یا «بدون تغییر» سریع ثبت کند.
- سیستم باید تفاوت قیمت احتمالی و قیمت نهایی را نشان دهد.
- اگر قیمت نهایی با قیمت احتمالی متفاوت بود، به‌صورت بصری مشخص شود.
- جمع کل نهایی محاسبه شود.
- وضعیت فاکتور:
  - PRE_INVOICE
  - PURCHASED
  - PENDING_FINAL
  - FINALIZED
  - SYNCED_TO_ACCOUNTING

بعد از ثبت نهایی:
- فاکتور باید سریعاً نوتیفیکیشن/الارم برای ADMIN ارسال کند.
- در نوتیفیکیشن نوشته شود: «فاکتور خرید نهایی شد و نیازمند ثبت در حسابداری است».
- لینک نوتیفیکیشن مستقیم به صفحه همان فاکتور برود.
- ADMIN بتواند فاکتور را مشاهده و سپس به‌عنوان SYNCED_TO_ACCOUNTING علامت‌گذاری کند.
- خروجی فاکتور نهایی برای انتقال به حسابداری در دسترس باشد.

========================
9) سیستم نوتیفیکیشن و الارم
========================

سیستم نوتیفیکیشن باید دو لایه داشته باشد:

1. In-App Notification
   - مرکز نوتیفیکیشن داخل برنامه.
   - Badge تعداد خوانده‌نشده در منو.
   - Toast هنگام انجام موفق عملیات.
   - لیست نوتیفیکیشن‌ها با زمان نسبی، مثل «5 دقیقه پیش».
   - کلیک روی نوتیفیکیشن کاربر را به صفحه مرتبط ببرد.
   - امکان خوانده‌شده کردن تکی و همه.

2. Web Push Notification
   - اگر کاربر اجازه داد و روی HTTPS بود، نوتیفیکیشن واقعی مرورگر/موبایل نمایش داده شود.
   - Service Worker باید پیاده‌سازی شود.
   - از web-push و VAPID keys استفاده شود.
   - در .env.example متغیرهای زیر وجود داشته باشد:
     - VAPID_PUBLIC_KEY
     - VAPID_PRIVATE_KEY
     - VAPID_SUBJECT
   - صفحه تنظیمات کاربر برای فعال کردن نوتیفیکیشن Push وجود داشته باشد.
   - اگر Push در دسترس نبود یا کاربر اجازه نداد، سیستم فقط In-App Notification داشته باشد و خطا ندهد.
   - برای iOS، در README توضیح بده که برای دریافت Push باید اپ به Home Screen اضافه شده باشد و HTTPS ضروری است.

رویدادهایی که باید نوتیفیکیشن بسازند:

- ثبت خرید دوچرخه جدید:
  - گیرندگان: ADMIN و STORE_MANAGER
  - پیام: «خرید دوچرخه جدید ثبت شد و نیاز به بررسی دارد.»

- ثبت هزینه جدید:
  - گیرندگان: ADMIN
  - اگر هزینه حقوق/پاداش/جریمه بود: STORE_MANAGER هم دریافت کند.
  - پیام مناسب با دسته هزینه.

- تأیید یا رد خرید دوچرخه:
  - گیرنده: ثبت‌کننده
  - پیام شامل وضعیت تأیید/رد و دلیل رد در صورت وجود.

- ایجاد وظیفه جدید برای کارگر:
  - گیرنده: کارگر/تعمیرکار
  - پیام: «وظیفه جدید برای شما ثبت شد.»

- ارسال انجام وظیفه توسط تعمیرکار:
  - گیرندگان: ADMIN و STORE_MANAGER
  - پیام: «وظیفه انجام شده و نیاز به تأیید دارد.»

- تأیید وظیفه:
  - گیرنده: تعمیرکار
  - پیام: «وظیفه شما تأیید شد.»

- رد وظیفه:
  - گیرنده: تعمیرکار
  - پیام: «وظیفه شما نیاز به اصلاح دارد.» + دلیل رد

- ایجاد پیش‌فاکتور خرید:
  - گیرندگان: ADMIN یا STORE_MANAGER بسته به نیاز، حداقل ADMIN برای اطلاع.
  - پیام: «پیش‌فاکتور خرید جدید ثبت شد.»

- نهایی شدن فاکتور خرید:
  - گیرندگان: ADMIN
  - اولویت: فوری
  - پیام: «فاکتور خرید نهایی شد و باید در حسابداری ثبت شود.»

- ثبت نهایی در حسابداری:
  - گیرندگان: STORE_MANAGER یا ثبت‌کننده مرتبط
  - پیام: «رکورد به‌عنوان ثبت‌شده در حسابداری علامت‌گذاری شد.»
